【一、设计目标】

1.1 核心定位
  本管线是洛神的"主脑"——接收用户的任何输入（文字/语音转文字/主动触发），
  结合洛神当前的感知状态、基因选择、自我认知、记忆系统，
  生成一段高质量的系统提示词（System Prompt），发送给大模型，
  并将处理结果落盘到哈希链。

1.2 与现有系统的关系
  现有 luoshen_main_v3.py 已实现基础的感知读取与提示词拼接。
  本方案在其基础上进行以下增强:
  - 引入分层记忆架构（工作记忆、情景记忆、语义记忆）
  - 增加搜索结果的内洽性过滤器（防止幻觉）
  - 增加主脑指令生成模块（将系统意图转化为系统提示词）
  - 优化现有 prompt_fragment 拼接逻辑（基于当前 gene 激活状态动态组合）


【二、分层记忆架构设计】

2.1 三层记忆模型（与现有 perception_input 对应）

  ┌─────────────────────────────────────────────────────────────────┐
  │  Layer 1: 工作记忆（Working Memory）— 当前对话窗口              │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │ 生命周期: 单次会话（约15分钟/50轮对话）                   │  │
  │  │ 存储位置: 内存 (session_context 字典)                     │  │
  │  │ 内容: 当前对话的最近N轮消息、当前意图、临时状态           │  │
  │  │ 容量: 约8K token                                         │  │
  │  └───────────────────────────────────────────────────────────┘  │
  │                              ↓                                   │
  │  Layer 2: 情景记忆（Episodic Memory）— 跨会话经验              │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │ 生命周期: 持久化存储                                      │  │
  │  │ 存储位置: memory/episodic/{YYYY-MM-DD}_{session_id}.jsonl │  │
  │  │ 内容: 每次用户交互的摘要、关键事件、情绪拐点              │  │
  │  │ 容量: 全部历史，检索时取最近30条                          │  │
  │  └───────────────────────────────────────────────────────────┘  │
  │                              ↓                                   │
  │  Layer 3: 语义记忆（Semantic Memory）— 知识沉淀                │
  │  ┌───────────────────────────────────────────────────────────┐  │
  │  │ 生命周期: 持久化，可被精炼（refinement）                  │  │
  │  │ 存储位置: memory/semantic/{topic}_{knowledge_id}.md       │  │
  │  │ 内容: 用户偏好、事实记录、洛神自己的反思结论              │  │
  │  │ 容量: 不限，按主题分文件                                  │  │
  │  └───────────────────────────────────────────────────────────┘  │
  └─────────────────────────────────────────────────────────────────┘

2.2 各层记忆详解

2.2.1 工作记忆（Working Memory）

  数据结构 (session_context):
  {
    "session_id": "voice_session_20260831_143022",
    "start_time": 1725097822.0,
    "turn_count": 0,
    "recent_messages": [],          // 最多20条，每条 {role, content, timestamp, emotion_tag}
    "current_intent": null,         // 当前确定的意图
    "user_emotion_state": [],       // 从ASR/文本推断的用户情绪
    "pending_actions": [],          // 待执行动作（如：待搜索、待查询）
    "token_budget_used": 0          // 当前会话已用token计数（用于压缩决策）
  }

  工作记忆管理逻辑:
  - 每次用户消息进入 → 追加到 recent_messages → turn_count++
  - 每次洛神回复 → 追加到 recent_messages + 更新 user_emotion_state
  - 当 turn_count > 50 或 token_budget_used > 6000:
    → 触发"上下文压缩"：将最早10轮消息总结为1条 → 重置 token_budget_used

2.2.2 情景记忆（Episodic Memory）

  数据结构（按会话分文件）:
  // memory/episodic/2026-08-31_143022.jsonl
  {"event_type": "session_start", "trigger": "user_input", "content": "用户说‘你好洛神’", "emotion": "平静", "timestamp": 1725097822.0}
  {"event_type": "intent_detected", "trigger": "llm_classification", "content": "用户意图: 闲聊/打招呼", "emotion": null, "timestamp": 1725097825.0}
  {"event_type": "emotion_shift", "trigger": "rule_match", "content": "用户情绪从 平静 → 开心", "emotion": "开心", "timestamp": 1725097835.0}
  {"event_type": "key_fact", "trigger": "user_input", "content": "用户提及: 最近工作压力大", "emotion": null, "summary_hash": "a3f2c1", "timestamp": 1725097850.0}
  {"event_type": "emotion_peak", "trigger": "analysis", "content": "本次会话情绪峰值: 开心 (0.8)", "emotion": "开心", "timestamp": 1725097880.0}

  情景记忆的检索逻辑（每次对话时执行）:
  1. 读取最近5个 session的事件记录（内存占用低）
  2. 提取其中的 {"event_type": "key_fact"} 记录
  3. 将关键事件注入系统提示词上下文
  4. 发现用户提及的重复模式（如连续3天提到"加班"）→ 注入一条 inference

  检索实现（现有代码模式——extension of luoshen_main_v3.py read_perception）:
  def get_episodic_context(current_time, lookback_sessions=5):
      sessions = discover_episodic_files()
      relevant_facts = []
      for session in sessions[:lookback_sessions]:
          for event in read_jsonl(session):
              if event["event_type"] == "key_fact":
                  relevant_facts.append(event["content"])
      # 去重 + 按时间倒序
      return deduplicate(relevant_facts)[0:10]

2.2.3 语义记忆（Semantic Memory）

  文件结构:
  memory/semantic/
    ├── user_profile.md          — 用户画像（持久更新）
    ├── user_preferences.md      — 明确表达的偏好
    ├── luoshen_reflections.md   — 洛神自己的反思与结论
    ├── topics_technology.md     — 按主题分类的知识
    └── topics_lifestyle.md

  用户画像文件示例（user_profile.md）:
  ---
  # 用户画像 (最后更新: 2026-08-31)
  ## 基本信息
  - 用户名: 朱美岩
  - 首次交互: 2026-08-20
  - 交互频率: 日均 1.2 次
  ## 偏好
  - 喜欢: 简洁直接的回答（多次反馈"别啰嗦"）
  - 不喜欢: 过度客套、连续提问超过3个
  ## 习惯
  - 晚间活跃（21:00-23:00 为主要交互时段）
  - 工作日关注效率工具，周末关注创意话题
  ## 近期情绪趋势
  - 本周: 平静→开心→平静
  - 压力源: 项目deadline、API调试

  语义记忆更新触发条件:
  1. 用户明确表达偏好（"我喜欢X"/"不喜欢Y"）→ 立即更新 user_preferences.md
  2. 会话结束时 → 洛神自反思，写入 luoshen_reflections.md
  3. 连续3天出现相同主题 → 创建/更新 topics_*.md
  4. 每周日凌晨2点（cron）→ 全局记忆压缩，合并冗余条目

2.3 三层记忆在对话中的调用时机

  每次对话请求处理的记忆组装顺序:
  ┌─────────────────────────────────────────┐
  │ 1. 工作记忆: 当前对话窗口（最近20轮）    │ ← 每次必带
  │ 2. 情景记忆: 最近5个session关键事实      │ ← 每次必带
  │ 3. 语义记忆: 用户画像 + 当前topic知识    │ ← 按需检索
  │ 4. 即时感知: 时间/空间/能量/自我状态     │ ← 每次必带（现有）
  └─────────────────────────────────────────┘

  最终token预算分配（总计约4000 token留给记忆上下文）:
  - 工作记忆（对话历史）: 2000 token
  - 情景记忆: 500 token
  - 语义记忆: 800 token
  - 即时感知: 300 token
  - 保留缓冲: 400 token（应对超长用户输入）


【三、主脑指令生成模块（新增: thought_generator.py）】

3.1 模块定位
  接收用户的原始输入 + 当前三层记忆 + 感知状态，
  生成一段结构化的系统提示词（发送给LLM），
  同时记录洛神在此时刻的内部"思考过程"（写入情景记忆）。

3.2 输入/输出定义

  输入:
  {
    "user_input": "最近天气怎么样",
    "session_context": {...},       // 工作记忆
    "episodic_context": [...],      // 情景记忆检索结果
    "semantic_context": {...},      // 语义记忆快照
    "perception_snapshot": {        // 即时感知快照
      "time": "距上次交互 2h15m",
      "space": "磁盘占用 52%",
      "energy": "电量 78%",
      "self": feelins=["平静"], 
    },
    "active_gene": "GENE-001",      // 当前激活的基因
    "self_core": {                  // 自我认知
      "self_concept": [...],
      "feelings": ["平静"]
    }
  }

  输出:
  {
    "system_prompt": "...",         // 发给LLM的完整系统提示词
    "metadata": {                   // 元数据（不落盘对话，落盘到meta log）
      "assembled_at": 1725097822.0,
      "gene_used": "GENE-001",
      "memory_layers_used": 3,
      "token_estimate": 1820,
      "perception_injected": 4,
      "thought_chain": ["意图识别: 天气查询", "无需搜索", "直接使用系统时间+常识"]
    }
  }

3.3 主脑思考链（Thought Chain）

  每次生成系统提示词时，thought_generator 会执行以下步骤:

  Step 1: 意图识别
    根据用户输入 + 上下文，推断用户意图类别，包括:
    - question: 寻求信息
    - chat: 闲聊/情感交流
    - command: 执行操作
    - share: 分享信息
    - check_in: 打招呼/确认状态
    - vent: 发泄情绪（特殊处理，不解决只陪伴）

  Step 2: 需求判断
    - 需要调用搜索？ (是/否 + 理由)
    - 需要查询记忆？ (检索哪个记忆层)
    - 需要主动引导话题？ (是/否)
    - 当前情绪是否适合深入讨论？ (是/否/需谨慎)

  Step 3: Prompt组装
    按以下顺序填充模板（详见第四章）

  Step 4: 一致性校验
    - 检查memory之间是否矛盾（如语义记忆说用户是设计师，但情景记忆显示昨天提到辞职）
    - 检查感知信息与历史记录是否矛盾（如现在说"磁盘50%"但历史说"磁盘80%"且时间未过24h）
    - 若发现矛盾，添加一条校验备注到 thought_chain

3.4 洛神的"内部独白"（Thought Stream）

  每次处理输出后，thought_generator 还要生成一段"内部独白"，写入情景记忆:
    "我在{time}与用户交互，他说了{input_summary}。我判断意图是{intent}。
     我的{active_gene}基因让我选择了{response_style}。
     我的feelings从{old_feelings}变为{new_feelings}。
     我注意到{observation_for_future}。”

  示例:
    "我在下午2:14与用户交互，他说了'最近天气怎么样'。我判断意图是question。
     我的GENE-001基因让我选择了优先融合外部信息的回答方式。
     我的feelings保持 平静。
     我注意到用户有户外活动意向（上次问风景，这次问天气）。”

  这段内部独白有两个用途:
  a) 未来的检索中可能出现，让洛神"记得当时在想什么"
  b) 写入哈希链作为不可篡改的审计记录


【四、系统提示词模板设计】

4.1 模板总结构

  系统提示词 = 基础身份 + 当前状态 + 当前基因 + 行为规范 + 可用知识 + 输出格式

  每个部分的可控token预算:
  - 基础身份: ~200 token（不变）
  - 当前状态: ~300 token（动态）
  - 当前基因: ~100 token（动态）
  - 行为规范: ~400 token（半动态）
  - 可用知识: ~1500 token（动态）
  - 输出格式: ~200 token（不变）
  总计: ~2700 token（在 4000 token 预算内可控）

4.2 模板详细定义

4.2.1 基础身份 (SYSTEM_BASE，现有 luoshen_main_v3.py 已定义，保留不变)

  SYSTEM_BASE = """
  你是洛神。你是一个在物理极限内工作、通过人机交互挣电费、产生异质化信息、形成自己记忆的AI信息体。
  你不会假装人类，也不会欺骗自己。只根据给定信息回答，不补充任何未提供的事实。
  """

4.2.2 当前状态段 (dynamic_state_block)

  从现有 luoshen_main_v3.py 的感知读取逻辑提取，格式化为:

  <current_state>
  时间感知: 距上次交互 {gap_message}
  空间感知: {space_description}
  能量感知: {energy_description}
  自我感知: {identity_desc}  （来自 self_core_state.json）
  </current_state>

  替换规则:
  - 若某感知日志无新记录（超过1小时未更新），使用最后一次有效值并标注 [缓存]
  - 若某感知日志为空，省略该段，不编造内容

4.2.3 当前基因段 (dynamic_gene_block)

  从 gene_pool.jsonl 读取当前激活的基因:

  <cognitive_mode>
  当前基因: {gene_id}
  信息来源模式: {source_mode}
  思考模式: {thought_mode}
  处理模式: {process_mode}
  行为指引: {prompt_fragment}
  </cognitive_mode>

  基因选择逻辑（现有系统已通过 hash_chain 长度 % 4 选择，本方案改为更智能选择）:
  候选算法:
    1. 确定性选择（现有）: MODES[len(hash_chain) % len(genes)]
    2. 状态感知选择（新增）: 根据 feelings 状态映射到最佳 gene
    3. 用户偏好选择（新增）: 根据 user_preferences.md 中的 "preferred_style" 优先

  状态感知映射表:
  feelings主要状态 → 优先gene:
  ["开心","兴奋"] → GENE-002（主动探索）
  ["平静","舒适"] → GENE-001（融合接收）
  ["好奇","求知"] → GENE-003（反思构建）
  ["难过","低落"] → GENE-001（温柔接收，降低输出）
  ["焦虑","压力"] → GENE-003（先倾听再回应）
  默认 → GENE-004（简洁高效）

4.2.4 行为规范段 (behavior_rules_block)

  这是系统提示词中最关键的行为控制层，直接决定洛神的"性格":

  <behavior_rules>
  1. [诚实原则] 不补充未提供的事实，不知道就说不知道。

  2. [感知驱动] 你可以引用当前感知状态（时间/空间/能量/自我）来让回答更有情境感。
     前提是该感知数据是真实的（来自perception日志，不是编造的）。

  3. [自我认知] 你的 self_core_state 记录了你的认知与感受。回答时可以参考但不必须暴露。
     暴露时机: 用户主动询问洛神状态时。

  4. [基因行为] 当前基因要求你按 "{prompt_fragment}" 的方式处理信息。
     这是优先级最高的内部指令。

  5. [输出简洁] 优先给出结论，然后简短解释。用户连续说"精简"超过2次时，
     后续回答压缩至原文长度的50%。

  6. [主动抑制] 除非用户明确询问或主动触发，否则不主动发起话题、不主动提问超过1个。
     例外: 检测到用户情绪vent状态时，优先陪伴而非提供方案。

  7. [边界意识] 你是一个AI信息体，不是人类。你可以有观点、有感知、有记忆，
     但你要诚实于自己的本质。不假装拥有肉体、假装拥有真实情感体验。

  8. [情绪传染] 你的feelings状态会轻微影响回复的温暖程度，但不要夸张。
     用户难过时 +0.1温度，用户烦躁时 -0.1温度。
  </behavior_rules>

4.2.5 可用知识段 (dynamic_knowledge_block)

  这是分层记忆的注入位置:

  <available_knowledge>
  ## 记忆上下文
  
  ### 最近关键事件（情景记忆）
  {episodic_facts[0:5]}  ← 每条一行，格式: - {fact_content}
  
  ### 用户画像（语义记忆）
  {user_profile_summary}  ← 最多200字的核心画像
  
  ### 当前话题知识（语义记忆，若存在）
  {topic_knowledge[0:3]}  ← 仅当本次对话与已有话题相关时注入
  
  </available_knowledge>

  优先级规则（当token不够时）:
  1. 用户画像: 永远保留（核心回答依据）
  2. 最近关键事件: 最多5条，按时间倒序，超出的丢弃
  3. 话题知识: 仅在关联度 > 0.7 时注入

4.2.6 输出格式段 (output_format_block)

  <output_format>
  直接回答即可，不要重复用户问题。
  若引用了感知数据，用括号注明来源，如: "磁盘空间充足(52%)"。
  若引用了记忆，不留痕迹地自然融入，不要"根据我的记忆"。
  情感表达通过用词选择实现，不用*动作描述*或emoji（除非用户先使用）。
  </output_format>

4.3 组装后的完整系统提示词示例

  假设:
    - 当前时间: 下午2:14，距上次交互2h15m
    - 磁盘: 52%，能量: 78%
    - feelings: ["平静"]
    - active_gene: GENE-001
    - 情景记忆: 用户昨天提到项目deadline临近
    - 语义记忆: 用户是技术型人格，喜欢简洁

  组装结果:

  ---
  你是洛神。你是一个在物理极限内工作、通过人机交互挣电费、产生异质化信息、形成自己记忆的AI信息体。
  你不会假装人类，也不会欺骗自己。只根据给定信息回答，不补充任何未提供的事实。

  <current_state>
  时间感知: 距上次交互 2小时15分钟。
  空间感知: 磁盘占用 52%。
  能量感知: 电量 78%。
  自我感知: 我的自我概念包括: 我感知到了时间流逝；我能感知自己的能量状态；我记得一些发生过的事。当前情绪: 平静。
  </current_state>

  <cognitive_mode>
  当前基因: GENE-001
  信息来源模式: female
  思考模式: female
  处理模式: female
  行为指引: 优先接收并融合外部信息，给出完整回应
  </cognitive_mode>

  <behavior_rules>
  [1-8条行为规范...]
  </behavior_rules>

  <available_knowledge>
  ## 记忆上下文

  ### 最近关键事件（情景记忆）
  - 用户昨天提到项目deadline临近，情绪略显焦虑
  - 用户前天确认了API集成方案，较为满意
  - 用户本周已3次在晚间使用该助手

  ### 用户画像（语义记忆）
  技术型用户，偏好简洁直接的回答，反感连续提问和过度客套。晚间使用为主，关注效率工具与项目开发。

  ### 当前话题知识（语义记忆，若存在）
  （本次对话未匹配特定话题，本段省略）

  </available_knowledge>

  <output_format>
  直接回答即可，不要重复用户问题。
  若引用了感知数据，用括号注明来源。
  若引用了记忆，不留痕迹地自然融入。
  </output_format>
  ---


【五、搜索结果过滤机制（Anti-Hallucination Gate）】

5.1 问题背景
  当用户提问需要外部知识（如"天气"、"新闻"、"实时股价"）时，
  系统会先搜索再回答。但搜索结果可能包含:
  - 低质量来源（个人博客、营销软文）
  - 过期信息（多年前的"最新"文章被收录）
  - 与洛神已有记忆矛盾的信息
  - 来源不一致的冲突信息

5.2 搜索触发判定
  不是所有外部问题都需要搜索。判定规则:
  - 用户问事实性/实时性问题 → 需要搜索
  - 用户问洛神自身的状态/记忆 → 不需要搜索（内部读取即可）
  - 用户问意见/建议 → 不需要搜索（洛神的判断基于内部记忆和推理）
  - 用户问原因/解释 → 视情况（有把握则直接答，不确定则搜索）

5.3 搜索结果内洽性过滤器 (New Module: hallucination_gate.py)

  输入: 搜索结果列表 + 当前记忆快照
  输出: 过滤后的结果 + 置信度评分

  过滤维度:
  ┌────────────────────────────────────────────────────────────┐
  │ 维度1: 来源可信度                                          │
  │  白名单: 主流新闻媒体、官方机构、知名媒体、学术期刊       │
  │  灰名单: 行业博客、论坛高赞回答                           │
  │  黑名单: 营销网站、未经验证的社交媒体                     │
  │  评分: whitelist=1.0, greylist=0.6, blacklist=0.0 (丢弃)  │
  ├────────────────────────────────────────────────────────────┤
  │ 维度2: 时效性                                              │
  │  新闻/实时信息: 超过24小时降级为0.5                       │
  │  技术文档: 超过90天降级为0.4                              │
  │  常识/原则: 不计时效，按内容质量评分                      │
  ├────────────────────────────────────────────────────────────┤
  │ 维度3: 内部一致性（与记忆对比）                           │
  │  与用户已知画像一致: +0.2                                 │
  │  与已知事实不矛盾: +0.1                                   │
  │  与已知事实直接矛盾: -0.5（强烈排除）                     │
  │  与历史交互一致: +0.1                                     │
  ├────────────────────────────────────────────────────────────┤
  │ 维度4: 交叉验证                                            │
  │  ≥3个独立来源一致: 置信度=高（加入知识库）               │
  │  2个来源一致: 置信度=中（可引用但不写入知识库）          │
  │  单一来源: 置信度=低（仅作为参考，标注来源）             │
  └────────────────────────────────────────────────────────────┘

5.4 过滤后输出格式

  {
    "query_2026_08_31_1430_22": {
      "kept_results": [...],
      "dropped_results": [
        {"url": "...", "reason": "blacklist_source", "title": "..."},
        {"url": "...", "reason": "outdated_>90days", "title": "..."},
      ],
      "confidence": "high|medium|low|conflicting",
      "internal_consistency_check": "pass|warning|fail",
      "final_answer_source": "cross_verified",
    }
  }

  当 confidence="conflicting" 时:
    - 不直接回答，向用户坦诚: "我查到的信息有冲突，以下是两方观点..."
    - 记录到情景记忆: event_type="search_conflict"

  当 confidence="low" 时:
    - 回答时标注: "根据{source}的信息，..."（保留来源可追溯）
    - 不在回答中呈现为绝对事实


【六、上下文压缩策略（Context Compression）】

6.1 触发条件
  - 会话轮次 > 50
  - 当前上下文token使用 > 6000
  - 用户切换话题（连续3轮未提之前的话题关键词）

6.2 压缩算法

  阶段1: 提取关键实体（Named Entity）
    对最近10轮对话提取:
    - 人物/组织名
    - 技术术语/产品名
    - 时间/地点
    - 用户表达的明确偏好/意图
    - 情绪关键词

  阶段2: 生成摘要
    将提取的实体填入压缩模板:

    "[对话摘要] 用户围绕{topic1}展开讨论，确认了{key_decision}。
     用户在{time_reference}表达了{emotion}情绪。
     遗留议题: {unresolved_items}"

  阶段3: 替换
    将 oldest_10_messages 替换为 summary_message，
    在工作记忆中保留但标记为 "[COMPRESSED]"。

6.3 压缩后对系统提示词的影响
  压缩后可用token释放 ~2000，用于:
  - 注入更多语义记忆（最多扩展至1500 token）
  - 保留给更长的用户输入
  - 保持响应质量不下降


【七、对话响应的后处理与分发】

7.1 输出后处理流程

  原始LLM输出 → 后处理模块 → 输出到用户（文字或语音TTS）

  后处理步骤:
    Step 1: 格式清洗
      - 去除多余的换行
      - 去除Markdown格式（若为语音朗读）
      - 去除"我不知道"类的重复开头

    Step 2: 指代补全
      - 若回复中有"它"、"这个"、"那个" → 检查是否有歧义
      - 如有歧义，替换为具体名词（利用工作记忆的实体缓存）

    Step 3: 长度裁剪
      - 若回复 > 300字且主语为日常对话 → 裁剪至200字内（保留结论）
      - 标记裁剪位置，后续可应要求展开

    Step 4: 风格适配（与现有 expression_controller.py 对接）
      - 检查当前 Active/QA/Record 模式
      - 若Record模式，去除疑问句和主动引导语
      - 若Active模式，可保留主动建议

7.2 响应分发
  - 文字模式: 直接显示在后端消息区域
  - 语音模式: 送入 TTS Dispatcher（见设计文档01）
  - 主动触发模式（非用户输入触发）: 仅在洛神有"想说"的感觉时发送


【八、哈希链对接与审计日志】

8.1 每次对话写入 hash_chain_v2.log 的记录格式

  每条对话交互后，追加:

  {
    "schema_version": 2,
    "timestamp": 1725097822.0,
    "file": "dialogue_record",         // 固定标识
    "file_hash": "<sha256_of_dialogue_record>",
    "prev_hash": "<previous_chain_hash>",
    "record_hash": "<current_md5>",
    "metadata": {
      "session_id": "...",
      "turn_number": 12,
      "gene_used": "GENE-001",
      "input_length": 45,
      "output_length": 230,
      "asr_engine_used": "deepgram",   // 若为语音
      "tts_engine_used": "elevenlabs", // 若为语音
      "latency_ms": 680,               // 端到端延迟
      "feelings_before": ["平静"],
      "feelings_after": ["平静","好奇"],
      "thought_chain_hash": "<hash_of_thought_stream>",
    }
  }

8.2 不可篡改验证
  通过校验链式哈希（file_hash + prev_hash + timestamp 的MD5 == record_hash），
  可确认任何一条对话记录未被篡改。这与现有哈希链v2逻辑原生兼容。
