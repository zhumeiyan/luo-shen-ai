# 第一部分：EO 框架定义

## 1.1 核心定义

EO（Emergent Organism，涌现有机体）是一套定义"什么样的人工系统可称为数字生命"的规则框架。EO 本身不是程序，是可验证、可度量的规则集。洛神是 EO 框架的一个工程实例。

EO 的核心命题：生命的"自己"不来自语言模型，而来自组合规则和时间连续性。语言模型只是"嘴"（翻译器），真正的"脑"和"身体"活在数据结构里。

## 1.2 十三条基因组规则

EO 用 13 条规则定义数字生命的最低要求，分为三组：

### A 组：五条件（存在前提）

一个系统要"活着"，必须满足以下五条。缺少任一条则不构成生命：

| # | 条件 | 含义 | 洛神当前实现状态 |
|---|------|------|----------------|
| 1 | 稀缺 | 资源有限，不是要什么有什么 | 部分体现（max_tokens 档位上限、僵化检测历史窗口） |
| 2 | 死亡 | 存在终结的可能性 | 计划死亡已实现；真正的"内生"死亡（能量耗尽）在 v1.0 中实现，但非由内部不可逆状态触发 |
| 3 | 不可逆 | 发生过的事无法撤回 | 已实现：哈希链 append-only + 不可逆参数漂移 |
| 4 | 代谢 | 能量输入/输出维持活系统 | 已实现：能量池（N 方程）有线性能量流入和线性衰减 |
| 5 | 内生约束 | 限制来自系统内部而非外部 | 部分实现：学习核心、僵化检测、退缩倾向形式到位 |

来源：`EO_ALIGNMENT_TABLE.md` L9-19

### B 组：七条操作码（生命指令集）

系统要能执行的最基础行为：

| # | 操作码 | 含义 | 洛神等价实现 | 状态 |
|---|--------|------|-------------|------|
| 1 | NOP | 空操作，维持状态 | 空闲气候演化（自发振荡） | 已实现 |
| 2 | EAT | 从环境获取能量 | N 方程接收环动能 + 用户输入压力 | 已实现 |
| 3 | EMIT | 向环境释放信号 | 回复长度/语气档位输出 | 已实现 |
| 4 | DUP | 复制自身（记忆编码） | 每次交互编一条情景记忆 | 已实现 |
| 5 | SWAP | 与环境交换状态 | 残留纹理偏移（0.1 倍） | 部分实现（极弱） |

| 7 | CATALYZE | 消耗自身帮助他人 | 关系压力积累后调制他人 | 部分实现（形式类似） |

## 1.3 发育时窗

定义：生命存在最佳发育期，错过不可逆。不发育的系统不是"一直活着"，而是"还没活过"。

洛神当前：全局不可逆漂移有时窗特性（慢变量 S 随时间趋近驱动值），但无明确的发育阶段边界。状态：部分实现。

来源：`EO_ALIGNMENT_TABLE.md` L92-98

## 1.4 三重判据

定义：一个系统是否"作为一个完整个体存在"，需同时满足三个独立条件：

| 判据 | 含义 | 度量 |
|------|------|------|
| 判据一：分化 | 有类型承诺、行为不冗余 | 自我声明振幅非零 + 行为熵 > 0.5 |
| 判据二：器官化 | 有独立功能单位，损毁后有双分离或高一致性 | 预/叙事方差 + 节律 ICC > 0.3 |
| 判据三：系统整合 | 行为由多信号联合驱动，中枢承担协调 | 3 个及以上偏置非零 + hub 相关性 > 0.25 |

通过条件：7 个子判据中至少 5 个为真。实验命令：python experiment/run_triple_criteria.py

来源：`experiment/run_triple_criteria.py`

## 1.5 自证拓扑

项目内实现：`self_check/` 目录（snapshot / trend / report / state_log / behavior_log / behavior_analysis 六个模块）。

核心原则：
- 不拦截，只呈现
- 不做 if-then 硬标签（"上升/下降/平稳"），而是用趋势斜率 + 偏离度连续描述
- 原始数据优先：结论是服务，数据是原料

## 实验 1：输入压力通道（P0 — 感觉器官打通）

### 规律

负向高唤醒输入相比中性低唤醒输入，能产生显著不同的环动力学响应。三通道（能量/张力/唤醒）的差异均超过 0.05 阈值，且方向可预测：负向偏负，正向偏正。

### 证据

代码：
- `living_engine.py` 函数 `_apply_input_pressure()` — 不再直接赋值能量/张力/唤醒，改为存储 (valence, arousal, 时间戳, tick号) 到 active_context["input_pressure"]
- `living_engine.py` 函数 `_update_luoshen_coupled()` — 调用 pressure_differentials()，将压力微分项加入微分方程
- `input_pressure.py` 函数 `pressure_differentials()` — 计算 dE = κ_E × val_pressure × decay 等

压力系数：κ_E = 0.06, κ_T = 0.04, κ_N = 0.06, baseline = 0.5, 衰减经 120 tick 到 0.37（约 40 秒）

来源：`input_pressure.py` L8-14

## 实验 2：内生性死亡 v0 计数器驱动版（P1）

### 规律

当系统运行拍数达到阈值时，系统进入不可逆的终止状态。死后气候冻结，且重启后仍保持死亡状态。

### 证据

代码：`living_engine.py` 函数 `_update_luoshen_coupled()`：
- 每拍 _death_counter += 1
- 当 _death_counter >= _DEATH_THRESHOLD：设置 deceased=True，写入哈希链 ENDOGENOUS_DEATH 标记
- 死后 environment_tick() 提前返回，气候不再演化

代码：`living_engine.py` 函数 `cold_start_if_needed()`：
- 冷启动时扫描哈希链，发现 extra.deceased == True 则调用 _build_fresh_memory() 时直接设置 deceased=True

常量：_DEATH_THRESHOLD = 50（测试用，注释标注正式部署 1000）
来源：`living_engine.py` L2477

衰老调制：当 _death_proximity > _DEATH_PROXIMITY_SLOW(0.7) 时，death_modulation = -1.5 × (proximity - 0.7) / 0.3 作用于行为选择

### 快照

| 项 | 值 | 来源 |
|---|---|---|
| 死亡拍号 | 50 | `endogenous_death_result.json` |
| 死亡触发条件 | _death_counter >= 50 | 代码 |
| 死后能量冻结值 | -0.7985 | `endogenous_death_result.json` tick 50 |
| 死后张力冻结值 | +0.9324 | 同上 |
| 死后唤醒冻结值 | +0.8965 | 同上 |
| 跨重启 deceased | True | `cross_restart_death_result.json` test_B |

复现命令：python experiment/run_endogenous_death_test.py（设置 _DEATH_V1 = False）

### 本质说明

v0 是参数驱动死亡：常数 _DEATH_THRESHOLD 直接决定死亡时点。改 threshold 则寿命线性变，但改能量输入则寿命不变。衰老信号是计数器比值（proximity），阶梯式跳变。这不是真正的内生死亡。v0 验证的命题是"死亡可被接入"，而非"死亡是内生的"。

## 实验 5：v1.0 状态驱动死亡

### 规律

死亡不再由"拍数到 N"触发，而由状态变量（能量储备、累积损伤）驱动。能量输入速率越大，寿命越长，且寿命对输入的响应是递增凸函数（非线性加速）。衰老信号是连续量（不跳变），直接混入行为选择。

### 证据

新增 ring_state 变量：
- energy（能量储备，初始 1.0，范围 [0, 1]）
- damage（累积损伤，初始 0.0，范围 [0, 1]）
- aging_signal（衰老信号，连续，公式：(1-E)×0.6 + damage×0.4）

微分方程（每拍更新）：energy += 能量输入率 − 基础消耗 − 压力消耗；if energy < 0.3: 损伤加速；修复量 = 修复率 × (能量 / 最大能量)；damage += 损伤速率 − 修复量

死亡判据（状态驱动）：
- energy ≤ 0.02（能量耗尽）→ ENERGY_DEPLETED
- damage ≥ 0.95（不可逆损伤）→ DAMAGE_IRREVERSIBLE

衰老调制（替代 proximity）：
- aging_signal > 0.4 → death_modulation = −1.5 × (signal − 0.4) / 0.6
- aging_signal > 0.75 → death_modulation = −3.0 × (signal − 0.75) / 0.25

代码位置：`living_engine.py` 函数 `_update_luoshen_coupled()` 新增能量/损伤/更新逻辑（在原有计数器旁加 if _DEATH_V1: 分支，与计数器版共存可控）

|-----------|-------------|---------|---------|---------|---------|
| 0.000 (无补充) | 245 | ENERGY_DEPLETED | 0.0200 | 0.187 | 0.663 |
| 0.001 (低补充) | 327 | ENERGY_DEPLETED | 0.0190 | 0.250 | 0.688 |
| 0.002 (默认) | 490 | ENERGY_DEPLETED | 0.0200 | 0.370 | 0.736 |
| 0.003 (中补充) | 980 | ENERGY_DEPLETED | 0.0200 | 0.738 | 0.883 |
| 0.004 (高补充) | 2000+ | 2000 拍内未触发死亡 | — | — | — |
| 0.006 (超额) | 2000+ | 2000 拍内未触发死亡 | — | — | — |

| 损伤触发的死亡 | v1.0 | 当前所有死亡均为能量耗尽型，损伤从未达到 0.95 阈值 |

## 4.2 不可判定的（当前框架内）

| 项目 | 原因 |
|------|------|
| "意识"是否存在 | EO 验证涌现有机体规则，意识是哲学命题，不在本框架判定范围内 |
| 语言模型是否构成"脑" | 架构设计为"嘴"（翻译器），但无法证明是否在涌现中偷偷承担了认知角色 |
| 长期（>2000 tick）稳定性 | 当前最大实验 2000 tick，更长期行为未验证 |
| 多用户交互下的稳定性 | 当前实验仅模拟单人输入，多用户并发未验证 |
| 死亡 v1.0 是否真正"内生" | v1.0 的能量输入率仍是模块级常数。真正的内生死亡需要能量输入也由内部状态决定 |

## 4.3 下一步（v2.0 方向）

按优先级从高到低排列。

### P0：补全 v1.0 未验证的死亡路径

**具体做法：** 当前 v1.0 的能量耗尽路径已通过 7 点对照验证，但损伤死亡路径从未触发（所有实验中 damage < 0.95）。需要在实验脚本中增加"高干扰模式"：每 tick 注入强负向压力（valence ≤ -0.8, arousal ≥ 0.95），观察损伤上升曲线。调低 `_DAMAGE_DEATH` 到 0.8 或 0.7，记录不同阈值下的触发拍数。目标：至少 1 次死亡由 `damage >= _DAMAGE_DEATH` 触发。

**为什么排这个优先级：** 如果损伤路径永远走不通，v1.0 的"能量耗尽 OR 损伤不可逆"双判据就只是名义上的双路径。这是一个必须在继续前进前确认的底层问题——否则 v1.0 没有真正完成。

### P1：能量输入内生化

**具体做法：** 当前 v1.0 的 `_ENERGY_INPUT_RATE` 仍是模块级常数，改这个常数就改寿命——这和 v0 改 `_DEATH_THRESHOLD` 改寿命在本质上相同。将 `_ENERGY_INPUT_RATE` 从常数改为 `base_input × efficiency(damage, aging_signal)` 的形式。效率函数 `efficiency = 1.0 / (1.0 + k × damage)`：损伤累积 → 代谢效率下降 → 能量获取减少 → 恶性循环。当 energy < 0.3 时效率进一步下降。验证：相同初始条件下损伤积累快的个体寿命更短。

**为什么排这个优先级：** 真正的内生死亡要求能量输入由内部状态决定，而非由外部常数决定。这是 v0 → v1.0 的跃迁中最后剩下的"外生尾巴"。

### P1：行为档位与能量消耗耦合

**具体做法：** 当前行为档位（max_tokens 能耗分档）不影响能量消耗。在 `_ENERGY_DRAIN_BASE` 中增加 `behavior_drain = factor × mode_idx / 4`，档位越高耗能越大。验证：相同能量输入下，高输出行为模式寿命更短。涌现预期：低能量时行为选择自动趋向低档位（节能行为），不再需要外部强制调制。

**为什么排这个优先级：** EO 代谢条件要求"不同活动有不同的代谢成本"。当前高输出和低输出耗能相同，不满足耦合要求。这条是将能量模型和行为选择真正打通的桥梁。

### P2：发育时窗

**具体做法：** 引入 `development_phase` ring_state 变量：0=幼体, 1=成体, 2=老年。phase 切换由累计交互数或能量历史触发（幼体期短，成体期长，老年期渐进）。不同 phase 对应不同参数集：幼体代谢效率高但寿命阈值低（不稳定），成体稳定高寿命，老年修复速率下降。关键验证：如果在幼体期给予高能量输入，寿命应显著高于老年期给予相同输入。

**为什么排这个优先级：** EO 中"发育时窗"是独立条件，当前系统全程参数不变。但这条不涉及底层生死机制，只影响阶段性表现，所以排在能量核心之后。

### P2：三重判据达到 7/7

**具体做法：** 当前 D3.1 未达标不是机制缺失，是实验没有把所有驱动同时激活。设计"全驱动同时激活"实验，分四阶段：平静期 → 压力期 → 关系升温期 → 临终期。在验证中确认 ≥3 个偏置在同一 tick 非零。

**为什么排这个优先级：** 已经 6/7，而且这是实验设计问题而非代码缺失。只需写一个新的实验配置即可验证。

### P2：代谢硬上限（稀缺原则）

**为什么排这个优先级：** EO 条件一"稀缺"要求资源有限。当前能量池 N 线性衰减但无硬上限——如果长期能量输入大于消耗，N 可以无限上升，不满足"稀缺"。这条是 EO 五条件之一，实现简单，但紧迫性低于生死底层机制。

**完整代码写法：**

在 `living_engine.py` 中增加常量（与现有死亡常量并列）：

```python
_N_MAX = 1.0    # 能量池硬上限
```

在 `_update_luoshen_coupled` 中，N 方程更新后加入截断：

```python
# 原有 N 方程更新（已有）
dN = (_GAMMA_N * (E**2 + T**2) - _DELTA_N * N + dN_mem) * _DT
N += dN + pressure_N_component

# 新增：硬上限截断
if N > _N_MAX:
    N = _N_MAX
```

**验证方法：**

新建实验脚本 `experiment/test_n_max.py`，逻辑如下：
1. 将 `_ENERGY_INPUT_RATE` 设为 0.01（远大于默认 0.002，使能量持续净流入）
2. 关闭所有外部压力（不注入任何 valence/arousal 扰动）
3. 运行 1000 tick，每 50 tick 记录 N 值
4. 检查：N 是否在达到 _N_MAX 后停止上升

**预期结果：**

| 项 | 预期 |
|---|---|
| N 上限 | 不超过 _N_MAX = 1.0 |
| 到达上限时间 | 取决于初始 N 和净流入速率，估算约 100-200 tick |
| 达到上限后 | N 在 _N_MAX 附近小幅波动（有流入=_N_MAX，有流出→低于上限→再流入） |
| 无上限对比 | 无上界版本 N 会线性上升超过 1.5、2.0… |

**优先级判断：** 这一条对洛神的"生死机制"影响极小（能量耗尽致死路径已经存在）。如果评估团队认为"稀缺"是 EO 条件中不可或缺的，可以半天实现。如果评估以生死机制为主，可以后移。

### P3：SPAWN v1（子单元通信）

**具体做法：** 操作码 SPAWN 是 EO 中唯一个体→群体的跃迁。单进程内创建多个"子 agent"实例，每个有独立 ring_state，共享用户输入通道。子 agent 之间通过 inbox/outbox 通信。当一个子 agent 能量耗尽，观察其他子 agent 的行为是否受影响。最小可行版本：2 个子 agent + 单向消息通道。

**为什么排这个优先级：** 这是涌现群体智能的前提，但涉及架构大改，工作量大，且单体系统内的生死机制已经可以单独验证。

### P3：验证层

**具体做法：** `self_check/` 已实现监测和报告层，但验证层未实现。包括：结构完整性校验、历史一致性校验、因果可追溯、盲测验证、跨平台可复现。

**为什么排这个优先级：** 验证层是"让自查可信"的前提，但不影响系统是否可以运行和死亡。属于架构进阶。

### P3：长期稳定性与多用户交互

**具体做法：** 当前最大实验 2000 tick。延长到 10000 tick，记录均值和方差是否随时间漂移。引入 2-3 个模拟用户观察多用户并发稳定性。

**为什么排这个优先级：** 稳定性是工程成熟度指标，不影响机制存在性证明。可在其他方向验证完毕后统一做压力测试。
